# Engine consistency checks: frozen models

This directory checks that models **exported by an older pero-ocr, torch or brnolm still load and give the same results** with the current code. It holds the checks and the committed models they run.

| file | what |
|---|---|
| `test_ctc_engine.py` | check: does a frozen CTC model still load in `PytorchEngineLineOCR` and read the same text and logits? |
| `test_transformer_engine.py` | check: does a frozen transformer still load in `TransformerEngineLineOCR` and decode the same text, with greedy and beam search? |
| `test_layout_engine.py` | check: does a frozen ParseNet still load in `LayoutEngine` and find the same baselines? |
| `test_lm.py` | check: does a frozen language model still load through `construct_lm()` and guide decoding the same way? |
| `data/` | the committed frozen models |
| `data/regenerate.py` | the script that recreates `data/` with the current code; all code used only for regenerating is in it (the models themselves are in `test/tiny_models.py`, because the engine tests build fresh copies of them in every session) |

The general engine tests are one level up in `test/engines/`.

## Why

The engine tests one level up run on tiny stand-in models that the test session builds **fresh** from the current code. A model built from the current code can never notice that the current code stopped accepting models built by an older one. For example, a change to how the engine reads the json, a renamed method the engine calls, or a torch upgrade that cannot load older torchscript files would all break models already deployed in production, yet every test using fresh models would still pass.

The models in `data/` close that gap. They were generated once and committed, so they act like models exported in the past. A failing check here means that previously exported models no longer work.

## What is in `data/`

Small, fake networks saved as torchscript, generated by `test/tiny_models.py`. They have no trained weights; their output is a deterministic function of the input.

| model | used by | behaviour |
|---|---|---|
| `ctc/` | `PytorchEngineLineOCR` | every horizontal run of bright pixels in the line crop becomes one character, `characters[1]`; with an embedding id `e` it becomes `characters[1 + e % (n - 1)]` |
| `transformer/` | `TransformerEngineLineOCR` (`exported: true`) | a line with *n* bright runs decodes to *n* characters `characters[1], characters[2], ...`, then the end-of-sequence token |
| `parsenet/` | `LayoutEngine` (ParseNet) | a baseline at the bottom row of every bright block, constant line heights, no line endpoints and no region separators |
| `lm/` | `construct_lm()`, `LMWrapper`, the `FAST-LOG-RAW` decoder | a brnolm torchscript LM (zip of `model.zip`, `decoder.zip`, `vocabulary.pickle`); its state is the last character seen, kept over line ends; after `a` it strongly prefers `b`, otherwise uniform |
| `<model>/generated_with.json` | | the commit and library versions that produced that model |
| `regenerate.py` | | recreates the models |

The OCR and layout models are saved twice, as `X` and `X.cpu`, because those engines append `.cpu` to the checkpoint path when they run on CPU. The LM loader does not.

Each model has its own `generated_with.json` because models are frozen at different times: `ctc`, `transformer` and `parsenet` at 81b496e, `lm` later, when it was added.

## How the data is made

pero-ocr's engines are mostly plumbing around a network: reading the engine json, finding and loading the checkpoint, padding and batching line crops, decoding, turning outputs into logits and confidences, and building the `PageLayout`. That plumbing is what breaks when code changes. Real models are a poor fit for testing it:

- They weigh hundreds of MB, and many of them are not public.
- They need a GPU to run in reasonable time.
- Their output is hard to predict, so a test can only check "something came out".

pero-ocr loads every network as a torchscript file and only calls it through a fixed interface: `forward(...)`, `encode` / `adapt` / `decode_step` for the transformer, or `model(x, h)` / `init_hidden()` / `decoder(o)` for the LM. So a tiny module that implements the same interface goes through exactly the same engine code as a real model. It fits in a few KB, runs on CPU in milliseconds, and gives an output a test can predict exactly.

"Ink" means bright pixels because the engines pad crops and pages with zeros, which is black. Bright-on-black test images (`test/synthetic.py`) keep that padding inert.

Real models are still needed to check recognition quality. That is the job of the separate GPU regression run on real data, not of these checks.

## Regenerating

Regenerate models **only on purpose**, and commit them together with the change that needs it:

    python test/engines/consistency/data/regenerate.py lm     # only the named models, e.g. a newly added stand-in
    python test/engines/consistency/data/regenerate.py        # all models, after a deliberate break of the model format

When you add a new kind of stand-in, name only that one, so the models that are already frozen stay untouched. The script builds the named stand-ins from `test/tiny_models.py` with the current code, rewrites their directories in `data/`, and records the commit and library versions in each model's `generated_with.json`. It works from any directory and always uses the `pero_ocr` of the checkout it lives in. pytest itself never writes to `data/`. After regenerating a model, its check compares the current code with itself until the model is old again, so anything that the old model exercised is no longer protected.

## When a check fails

1. A failure means a model exported by an older version stops loading or behaves differently.
2. If that is **not intended**, fix the code: deployed models depend on it.
3. If it **is intended**, it is a breaking change for every deployed model. Announce it, make sure the production models are re-exported, then regenerate the data as described above.

Never regenerate the models just to make a failing check pass.
